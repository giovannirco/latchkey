# Security

## Reporting a vulnerability

Report it privately through GitHub: the "Report a vulnerability" button on the repository's Security tab, or [this form](https://github.com/giovannirco/latchkey/security/advisories/new). Please do not open a public issue. Include the firmware version and board from `system.info`, what you did and what happened. Only the latest release is supported while Latchkey is at 0.x.

## Status

Latchkey is in early development. This document describes the security design of the current tree; v0.5.0 is the latest release and `CHANGELOG.md` identifies unreleased changes. What is not built yet and what is still unverified on hardware is listed in [docs/v1-readiness.md](docs/v1-readiness.md).

## The model in plain words

The owner is whoever holds the owner password and the TOTP secret, and whoever is physically at the board.

- **Claiming happens over USB only.** A fresh board has no owner. `system.setup` (Wi-Fi with a static IPv4 address, owner password) is accepted only on the USB serial console; it returns the TOTP secret once, as an `otpauth://` URI. A claimed board refuses a second claim.
- **USB serial counts as physical presence.** Requests over the serial console need no session and no button press: that includes `system.factoryReset`, which from the web also needs a press of the board's button, and `system.time.set`, which only the console accepts. Anyone who can plug into the board's USB port can therefore reset it and claim it again, and a compromised computer left connected to the board can run destructive actions without a press. Keep the board where only you can reach it, and do not leave it connected to a computer you do not trust.
- **Owner password.** Stored as PBKDF2-HMAC-SHA256 with a random 16-byte salt. The cost is 4400 iterations, about 1 s on the classic ESP32 at 160 MHz and about 0.6 s on the ESP32-S3; it is stored with the hash, so a later firmware can raise it without breaking an existing claim. The password itself is wiped from memory after hashing, and `auth.changePassword` hashes the new one with a new salt at the current cost. Salt, cost and hash are one NVS item, so a password change that fails half way leaves the old password working. A login also needs the TOTP code and slows down after failures (below), so the hash cost is not the only protection against guessing the password.
- **TOTP.** RFC 6238 with SHA-1, 6 digits and 30-second steps; the 20-byte secret is generated on the board when it is claimed. Login asks for the password and a current code, accepting one step of clock drift either way. The board checks both every time and compares them in constant time, so the reply time does not tell which one was wrong. A code whose step was already accepted is refused, so a code seen once cannot be used again, and the last accepted step is kept in NVS across reboots. Codes are refused with `time_unsynced` until the clock is set by SNTP or by `system.time.set` over USB. `auth.rotateTotp` replaces the secret (from the web, after a press of the board's button) and returns the new `otpauth://` URI once; the old secret stops working at once, and every session but the caller's ends.
- **Login rate limit.** Five failed logins in a row start a 30-second wait that doubles with each further failure, up to 15 minutes; during the wait every login is refused with `rate_limited` before any check runs, and the next successful login resets the count. The count is kept in NVS, so a reboot or a power cut does not reset it (the wait starts again in full); it is written only when it changes, at most ten times per lockout. If the stored count or the last accepted code step cannot be read at boot, the board assumes the worst: the longest wait, and the codes of the current window refused. A wrong current password in `auth.changePassword` counts as a failure too. The limit is global, not per client: anyone who can reach the board on the network can keep the web login closed by sending one wrong attempt per wait. The USB console needs no login and keeps working through a lockout; keep the board on a network you trust, such as your own IoT network, not one shared with guests.
- **Web sessions.** A web login opens a session identified by a random 256-bit token; the board keeps only the token's SHA-256, in RAM, so a reboot ends every session. A session ends after 15 minutes without a request and 12 hours after the login; at most four exist, and a fifth login replaces the one used least recently. `auth.sessions`, `auth.revoke` and `auth.logout` list and end them, and `auth.changePassword` and `auth.rotateTotp` end all but the caller's. The token travels in a cookie marked `Secure`, `HttpOnly` and `SameSite=Strict`, never in a JSON body, and the API accepts only JSON (`Content-Type: application/json`, at most 256 values, counted before parsing) and only requests whose `Host`, and `Origin` when present, name the board's own IP address, which also stops DNS rebinding. The event WebSocket opens only with a valid session cookie under the same address rules, and closes within seconds of its session ending. A web job checks its session when it starts and again after the button press. ESP-IDF's HTTP server keeps its own copy of the request headers, the session cookie included, for asynchronous handlers and frees it without wiping it, so a token can linger in freed RAM until it is overwritten; this is a limit of the framework, and a reboot ends every session anyway. Over USB, `auth.login` takes `dryRun` and only checks the password and code.
- **Button confirmation.** Destructive actions requested from the web wait up to 30 seconds for a press of the board's button and fail with `confirm_timeout` without one: today pairing, factory resets of the board or a lock, rotating the TOTP secret, showing or changing a lock's keypad admin passcode, encrypted key export and import, and running lock hardening. Hardening preview is read-only and asks for no press. Switch writes refuse before asking because their layout is unverified. A request with bad parameters or a refused precondition fails before the wait, so a press never confirms a request that cannot run. The board announces the wait with a `confirm.required` event and the outcome with `confirm.result`. `locks.forget` needs a session but no press: it drops the keys on the board only, and the lock keeps working with any other board that holds them. A job's result (the new `otpauth://` URI of a rotation, for one) goes only to the event sockets of the session that asked, never to the serial console or another session.
- **HTTPS.** The first time it has an address, the board generates its own EC P-256 key and self-signed certificate (TLS 1.2, valid from 2024-01-01 with no expiry date) and keeps them in NVS until a factory reset. The certificate's SHA-256 fingerprint is shown on the serial console and in `system.info`: compare it with what the browser shows the first time you connect. Plain HTTP only redirects to HTTPS. Every response carries a hash-based Content-Security-Policy, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff` and `Cache-Control: no-store`. The server keeps three connections on the classic ESP32 and four on the ESP32-S3 and drops the least recently used one for a new one, and it reads request headers on its single task, so anyone on the network can keep the web UI busy, for example by sending headers very slowly; a TLS handshake that does not finish within 3.5 s is dropped. Keep the board on a network you trust.
- **Audit log.** The last 200 actions, each with the time, the origin (serial, web, mqtt, or `board` for unlock alerts the board raises itself), the method, the target and the result, kept in NVS; `audit.list` reads them. Methods can add entries but not change them; `system.factoryReset` clears the log. Entries never contain secrets. Login attempts whose password and code were checked are logged, whatever their origin, and the rate limit keeps those to one per wait. Not logged: logins refused before any check (rate limit, unset clock, malformed request), and any other request from the web that carries no valid session, so a stranger cannot wear out the flash by sending them.
- **Logs.** The board keeps its latest log lines in RAM (about 100 on the classic ESP32, 300 on the ESP32-S3), wiped at every start, including the restart after a factory reset (on the classic ESP32 they sit in RTC memory, which a restart alone would keep), and the owner reads them with `system.logs` or on the System page. They hold what the USB console prints as log lines, never its replies or events. Secrets are never logged; as a second line of defence, a line shaped like one (an `otpauth://` URI, a `secret=` parameter, the session cookie, a JSON member holding a password, code or backup, or a run of 32 hex or base32 characters) is kept only as a notice and counted in `system.info.logs.withheld`, while the console still prints it. A four to nine digit passcode cannot be told apart from other numbers, so for passcodes the protection is that the code never logs them.
- **Remote logging** (off until configured with `system.syslog.set`). The board sends its log lines as RFC 5424 syslog over plain UDP or TCP, without TLS, to the collector you name: anyone on the network path can read them, and could drop or forge lines on their way. The lines never hold secrets, but they name the board, its address and the Bluetooth addresses of its locks, and say when the doors were operated. Put the collector on your own network and keep its logs to people you trust; nothing checks that the host you name is on your network.
- **Unlock alerts.** The board reads each lock's operation log after the connections it makes anyway and about every six hours otherwise, and raises `lock.alert` with an audit entry (source `board`), an MQTT message where that is set up, and a notice in the web UI for every unlock from an app or a gateway it did not make and every forced opening. This catches, after the fact, unlocks by someone who copied or broke the lock's Bluetooth keys. It matches its own unlocks by the record id returned by the lock. Only an attempt without a returned record id uses a time window (120 s either side, one log record per request); a foreign unlock inside that window can be mistaken for the board's own. Another board holding the same keys, such as one restored from a backup, raises alerts on this one. The board remembers at most 16 unmatched unlocks per lock in RAM for 24 hours. An unlock displaced by newer requests or older than that window can raise a false alert when its log record is eventually read. A restart after its unlock but before the log read can raise a false alert for that unlock. Records the lock wrote before the board first read its log are not judged, and an alert waits for the next read: up to about six hours for a lock nothing else connects to. The board keeps the current and preceding clock offsets; timestamps from older offset periods can be inaccurate. The newest eight unacknowledged alerts per lock survive a board restart in NVS, with storage protected by the reserve. Acknowledging a displayed alert id leaves later arrivals unread. A corrupt saved cursor creates a persistent monitoring warning, also reported by `system.info`, without sending an unexpected-unlock MQTT event. If the stored alerts cannot be read, the board starts a new list holding a persistent warning that they were lost (in `locks.list`, the web UI and `system.info`, never sent as `lock.alert`) and keeps reading the log and setting the lock's clock. If an alert cannot be saved, it is still announced (event, audit entry, MQTT), and its log page is retried before the cursor advances. Deduplication holds eight entries; a longer backlog combined with failed cursor storage can repeat notifications after older entries are displaced. Exactly-once delivery is not guaranteed. Acknowledgement is serialized with monitoring and refuses while alert or cursor durability is unresolved. Stored alerts can require a complete successful catch-up after restart before acknowledgement; unknown alert times remain unknown instead of taking the retry time. Dedicated log connections require an advertisement within the last three minutes. Whether a lock's log starts over when it is full is unverified.
- **Secrets stay on the board.** Lock keys, the owner hash, TOTP secrets, session tokens, network passwords and passcodes never enter logs or audit entries. The encrypted backup is returned only to its requesting owner session or USB caller. Explicit passcode creation and button-gated admin-code views retain their documented replies; TOTP setup/rotation returns its one-time `otpauth://` URI. Operation-log passcodes never leave the board. Backup passphrases and plaintext keys never appear in RPC results or events.
- **Partial lock hardening** (`lock.harden`). A read-only preview reports prerequisites and planned steps without a button prompt, storage mutation or audit write. Explicit execution requires a backup and synchronized clock, then confirms with the board button from the web and rechecks state. It synchronizes time, removes known unmanaged passcodes and rotates only a confirmed pairing-generated admin code. Managed codes, current/pending admin copies, owner-managed or unknown-origin admin codes and unknown passcode types are preserved. Reset-button writes always remain skipped as unverified: even successful execution reports partial completion and `hardened:false`. A failed step stops further mutations and reports completed work; reporting or connection failure may leave confirmed changes applied, so the UI requires a fresh preview before another explicit attempt.
- **Pending admin changes.** A candidate is persisted separately from the confirmed old copy before a write. A lost acknowledgement or interrupted persistence retains recovery evidence. Authenticated readback can confirm either copy; an unavailable or different readback blocks further rotation. A later owner change request reconciles only and answers `admin_reconciled` or `admin_unresolved`, never silently sending another code. Backup preserves both copies and provenance.
- **Key backup** (`keys.export` and `keys.import`). Lock keys leave the board only inside an authenticated AES-256-GCM envelope, with its header authenticated and its key derived by PBKDF2-HMAC-SHA256 (100,000 iterations), a random salt and nonce. Passphrases are 12 to 128 UTF-8 bytes, preserved exactly, with NUL refused. A backup includes selected lock records, labels, seeds and pending admin recovery, excluding board credentials, network settings, audit history and monitoring cursors. Plaintext is bounded to 8 KiB and the file to 8,246 bytes; export individual locks if the complete set does not fit. Import validates everything and refuses existing identities or insufficient capacity before mutations. A durable journal rolls back only newly imported identities after write failure or restart; failed cleanup blocks lock initialization. Forget and board reset refuse erasure of reset-button-off locks and unreadable recovery records with `recovery_protected`, even with `force`. The [backup and hardening contract](docs/backup-hardening.md) has the details and the offline evidence.
- **MQTT for Home Assistant** (off until configured with `mqtt.set`). The board speaks plain MQTT 3.1.1 over TCP, without TLS: anyone who can watch the network between the board and the broker sees the broker username and password at each connection, the lock states and the commands, and could inject commands into that connection. The board connects to whatever host the settings name, and nothing checks that it is on your own network: put the broker there, give each board a user of its own, and use a broker that refuses anonymous clients. TLS to the broker is not supported yet.
  - What a broker user can do: whoever may publish to `latchkey/<board>/<lock>/set` can lock and unlock that lock, with no password, TOTP code or button press, exactly as Home Assistant does; whoever may subscribe under `latchkey/<board>/` sees each lock's state, battery, last event, link and unlock alerts; whoever may publish the board's own topics can fake the retained state and alerts that Home Assistant shows. Nothing else is reachable over MQTT: no pairing, no keys, no passcodes, no settings, no reset. Give the board's user write access to exactly `latchkey/<board>/availability`, `latchkey/<board>/+/state`, `latchkey/<board>/+/battery`, `latchkey/<board>/+/last_event`, `latchkey/<board>/+/link`, `latchkey/<board>/+/alert` and `<prefix>/+/<board>/+/config`, and read access to `latchkey/<board>/+/set` and `<prefix>/+/<board>/+/config`; let only Home Assistant's user write the `set` topics, and nobody else the board's topics. With those rules nobody else can publish where the board listens. A message there whose topic does not fit the board's 256-byte MQTT buffer ends the connection (a limit of the MQTT library), and a retained one would end every reconnection.
  - Every MQTT command that runs is audited with the source `mqtt`. The board subscribes only to the `set` topics of the locks it holds and takes one queued command per lock; refused commands (one already queued, a full job queue, an overflowing board queue) are counted and audited together, at most one entry a minute per kind, so a flood of messages cannot churn the audit log or wear out the flash that holds the lock keys. A retained command is ignored, because the broker would deliver it again at every reconnection; so is any other payload, with at most one log line a minute.
  - The MQTT password is stored in NVS like the Wi-Fi password (profile P1), is accepted by `mqtt.set` but never returned (`mqtt.get` only says whether one is set), and is never logged or audited. A settings change that names another host, port or username clears the stored password unless it gives a new one, so the password cannot be sent to a broker of someone else's choosing. The board's MQTT task keeps a copy only while MQTT is on and wipes it when MQTT is turned off; the MQTT library keeps its own copy while it runs and frees it without wiping it, and a reboot clears that.
  - Changing the MQTT settings needs an owner session from the web, like the other settings: a stolen session could point the board at another broker, which then receives the lock states and can send commands, so treat a session as the key to the door it already is.
- **No cloud.** The board talks to the lock over Bluetooth LE and to your browser, and to your MQTT broker and syslog collector when you turn them on, over your own network. Its only traffic to the internet is DNS and SNTP time queries to `pool.ntp.org` and `time.cloudflare.com`, because the lock protocol needs the correct time. There is no TTLock account, no phone app and no telemetry.

## Security profile P1

Latchkey targets one threat profile, P1: someone may get hold of the board, but will not read its flash chip.

- Lock keys (the lock's AES key, `adminPs`, `unlockKey`, the admin passcode), the offline-code seed table pairing sends, the owner password hash and the TOTP secret sit in NVS in plaintext. Passcodes are not stored on the board: it keeps only their names and ids, which are derived from the lock's key, and shows a code once, when it is added. Confidentiality at rest is not claimed: whoever reads the flash of a stolen board can operate the locks it manages.
- Flash encryption with NVS encryption (`nvs_flash_secure_init()`, profile P2) protects against that, but it is opt-in and not the default. It burns eFuses in the chip, which cannot be undone, and a mistake during that step can leave a board that never boots again. An encrypted board also no longer takes the plaintext release images or the browser flasher, so updates and recovery get harder. Latchkey does not ship a P2 configuration yet; owners who accept those costs can build one.
- In practice: mount the board indoors, out of reach from outside the door. If a board is lost or stolen, treat the keys of its locks as known to someone else: restore the encrypted backup on another board, factory-reset each lock from there and pair it again (a two-board restore is not yet verified on hardware); a lock whose reset button is still enabled can also be reset at the lock.

## Limits of the TTLock protocol

These come from the locks and are outside Latchkey's control; [docs/protocol.md](docs/protocol.md) has the details.

- Before pairing, every lock uses the same public AES key, and the lock sends its own key during pairing encrypted only with that public key. Someone who records the Bluetooth traffic of a pairing learns the lock's key. Pair where nobody else is within Bluetooth range.
- Frames are AES-128-CBC with the key as the IV and no message authentication. Lock and unlock answer a random challenge the lock sends first; whether a given lock rejects a replayed frame depends on its firmware and has not been tested by this project.

## Out of scope

- Reading the board's flash, or any attack that needs the board in hand (profile P1).
- A compromised computer connected to the board's USB port.
- Physical and mechanical attacks on the lock, its keypad, fingerprint and card readers, and its own firmware.
- Bluetooth or Wi-Fi jamming, which can stop the board from reaching the lock but not open it.
- Reproducible builds: they are not claimed. Release images are built by GitHub Actions from the tagged commit with the pinned toolchain.

## Supply chain

- The toolchain is pinned: PlatformIO Core 6.2.0, `espressif32@8.0.0` (ESP-IDF 6.1.0) with exact package versions in `platformio.ini`, and the ESP-IDF managed components locked per target in `dependencies.lock.esp32` and `dependencies.lock.esp32s3`.
- Every GitHub Action is pinned to a full commit SHA. Each job gets only the permissions it needs, CI needs no secrets, only the release job can write releases and only the Pages job can deploy the site.
- Each release publishes `SHA256SUMS` next to its images. The browser flasher serves the images from the same origin as the page and loads ESP Web Tools 10.4.0 from unpkg with every module pinned by its SHA-384 hash, so a modified file is refused by the browser. To avoid third-party code altogether, check the image against `SHA256SUMS` and flash it with esptool ([docs/hardware.md](docs/hardware.md)).
