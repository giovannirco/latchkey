# Encrypted backup and hardening

The owner authorized backup/hardening application code and offline tests on 2026-11-09 UTC. OTA, flashing, real-device operations and unverified switch writes remain excluded. This work does not prove recovery on hardware.

## Backup contract

`keys.export {passphrase, lock?}` returns an encrypted backup; `keys.import {passphrase, backup}` restores it. Both require owner authentication and the board button over HTTPS; USB retains the existing physical-presence rule. Web requests use jobs; USB keeps its inline reply contract. Passphrases are 12 to 128 UTF-8 bytes and never enter logs, events or audit metadata. The JSON transport rejects U+0000 explicitly because its string representation cannot preserve embedded NUL characters; it must never silently truncate a passphrase. Other valid UTF-8 controls remain supported by the length-delimited crypto interface.

Use a versioned `LKB2` binary envelope: magic, version, KDF identifier, PBKDF2-HMAC-SHA256 iteration count (100,000), 16-byte random salt and 12-byte random nonce. Authenticate the complete header as AES-256-GCM additional data; use a 16-byte tag. Reject unknown versions/KDFs and unexpected iteration counts before deriving a key. Reuse the existing PBKDF2 implementation and PSA cryptography; add no dependency. Derivation yields periodically to the scheduler.

Encode fields explicitly, not as raw C++ structs. Preserve each lock's identity, protocol and keys, confirmed admin-passcode copy/provenance and any pending replacement, labels (including managed flags and weekly schedules), and optional seed table. Exclude board credentials, Wi-Fi/MQTT configuration, audit history and monitoring cursors. Validate counts, lengths, flags, UTF-8 text, MAC uniqueness, protocol data and nested records before any storage mutation. Clear transient plaintext and key material on success and failure.

Bound plaintext to 8 KiB, accepting up to eight locks when they fit. Refuse oversized exports with an instruction to export individual locks; never truncate or silently omit data. A maximum-size single-lock fixture must fit. Bound the authenticated RPC body and serial line to 16 KiB; buffers grow on demand rather than reserving that space permanently. Authenticate before allowing the larger HTTP body; unauthenticated login retains its smaller limit. Transfer parsed job parameters instead of duplicating them, release the raw request before starting the job, and release encoded input before allocating decoded records. Prefer a single owned binary buffer for authenticated decryption; PSA permits overlapping input/output buffers, but plaintext is unusable until authentication succeeds. Check allocation failures and test buffer lifetimes; runtime heap remains unproven. Increase the browser backup timeout to cover button confirmation and derivation.

Also bound export serialization and queued WebSocket bytes. Release binary/JSON representations as soon as their serialized replacement owns the data, and reject work that cannot meet the allocation budget. Test maximum import/export payloads against an explicit allocation budget; queue limits by message count alone are insufficient for large results.

Wrong passwords, damaged blobs, duplicate identities, existing locks, insufficient capacity or failed validation change no stored lock. Existing locks are reported and never overwritten, including persisted identities whose records are unreadable and absent from the in-memory lock list. Preflight the whole import and the NVS reserve. Persist a journal of new identities before writing their records, labels and seeds; publish the import only after every write succeeds. On error or reboot, remove only the journaled new identities, retain the journal if cleanup fails, and refuse lock initialization until recovery succeeds. Serialize imports with other lock mutations. Export refuses unreadable source records and marks the selected locks backed up only after encryption succeeds; return an error if this state cannot be persisted.

## Hardening contract

`lock.harden {lock, dryRun?}` previews or runs an ordered plan: time synchronization, unmanaged-passcode removal, admin-passcode handling, reset-button handling. Preview is read-only and reports opaque passcode IDs and counts, never codes. Its serialized read path bypasses automatic catch-up, clock writes, label pruning, reconciliation persistence and audit storage; authentication and read commands alone are allowed. An uncached feature mask is read into the session without persisting it. The optional `dryRun` must be a boolean; omitting it requests execution. Preview reports `executable: false` when a backup or synchronized board clock is missing, or admin state/readback remains unresolved. Unknown legacy provenance preserves the admin code and does not by itself block cleanup. Execution requires a backup since pairing and the board button over HTTPS, and rechecks current lock state after confirmation. Managed passcodes, confirmed and pending admin copies, and the authenticated current admin readback are never deleted. Known unmanaged cyclic passcodes use the existing deletion command; no weekly creation or editing command is added. Stored labels and weekly schedules are not pruned during either hardening mode. Unknown passcode types are preserved.

Record admin-passcode provenance explicitly for newly paired locks and successful owner changes. Preserve owner-selected codes. Preserve legacy codes whose provenance is unknown, report that uncertainty and direct the owner to the existing admin-passcode control; do not guess provenance from code length. Rotate only a confirmed code known to be generated at pairing. Record a successful hardening rotation as `HardeningGenerated`, so a later partial retry does not rotate it again. Owner-invoked random changes are `Owner`. Avoid collisions with listed passcodes, persist confirmation accurately and never overwrite a confirmed old copy before the lock accepts the replacement. New codes do not appear in progress events; the existing button-gated admin-passcode view remains available.

Before any admin-code write, persist the candidate separately from the confirmed old copy. A timeout or reboot retains both and marks the outcome unresolved; no automatic retry or further rotation occurs. Authenticated readback may confirm the candidate or the old code, then persist the confirmed record and provenance before removing the pending entry. Record and metadata writes are independently durable; an interrupted transition can retain equal confirmed and pending copies with the pending target provenance until reconciliation completes. A write can durably complete while returning an error: that request reports failure, but a later strict read or restart may accept a fully persisted confirmed record plus target provenance and cleared pending entry as resolved. Incomplete or unreadable transitions retain pending evidence and require authenticated readback. If readback is unavailable, fails, or reports a third code, retain the pending state and refuse automatic rotation. Backup/import preserves this state. Confirmed refusal may clear the candidate; failed cleanup remains visible and blocks further rotation.

Report each step and stop further mutations on an actual failure. The pre-clock log read stops at the first alert-save failure without publishing that alert, writing its audit entry or saving later alerts; only the final hardening-failure audit follows. The failed alert remains eligible for delivery on a later monitoring read. Ordinary monitoring retains its alert-delivery behavior when storage fails. Direct hardening jobs close both new and reused links before returning, so neither a preview nor a failed execution enables opportunistic monitoring writes on its retained link. Independently scheduled monitoring remains active. Reset-button writes are always skipped as unverified in this version; `hardened` stays false while a required step is skipped or failed. Return explicit completion state and step results. The UI must display partial completion and never infer success from the presence of a result object.

Persist backed-up, hardened, reset-button-off and provenance flags without reinterpreting existing flags. Guard local forget and board factory reset while any affected lock is recorded with its reset button off. Enumerate persisted identities, including entries missing from the live manager list. Corrupt or unreadable records or metadata refuse erasure. Absent metadata retains the established legacy defaults and does not itself block erasure. No force bypass is introduced. Pairing clears lifecycle flags. Imported recovery status must accurately reflect the authenticated backup and the current restore.

## Hardening RPC results

Successful preview and partial execution return a result with `dryRun`, `completion`, `executable`, `hardened` and `steps`. `completion` is `preview` or `partial`; `hardened` is always false. `executable` describes the prerequisites observed while constructing the plan and is not a completion flag. Execution clears any previously stored hardened flag before beginning the time step, while retaining the other lifecycle and recovery fields.

`steps` always orders `time`, `passcodes`, `admin`, `resetButton`. Each entry has `step` and `status`: `planned`, `preserved`, `done`, `skipped` or `failed`. A failure adds a nonsecret `error` code. The passcodes step also has `planned`, `removed`, `preserved` counts and `entries` containing only opaque 12-digit hexadecimal `id`, `status` and `reason` (`managed`, `admin`, `unmanaged`, `unknown`). Labels and PINs are absent. The admin step has a `reason` of `owner`, `legacy_unknown`, `hardening_generated`, `pairing_generated`, `confirm_candidate`, `confirm_previous` or `admin_unresolved`. The reset step always has status `skipped` and reason `unverified_switch_layout`.

An execution step failure returns RPC error `hardening_failed` with the same fields flattened into the error object, including `completion: "failed"` and all step details. The existing audit path therefore records failure. Validation, storage prerequisites, button/session refusal and read failures before a plan is available return ordinary RPC errors. Result allocation/serialization failure returns `internal`; it never turns a missing result into successful `{}`. Changes already confirmed on the lock remain durable, so refresh state before retrying after a reporting failure.

The UI must inspect `completion` and step statuses, including those in error responses. A completed job or an RPC result object does not establish full hardening. No switch write is sent, and the handler emits no PIN-bearing progress events.

The existing `lock.adminPasscode.set` success shape is unchanged. When a pending candidate exists, a later owner request performs authenticated reconciliation only. It returns `admin_reconciled` when that verdict was stored, requiring review before another explicit change; it returns `admin_unresolved` if readback, persistence or refusal cleanup remains uncertain. Neither outcome sends another admin-code write. Timeout/disconnection errors retain pending recovery evidence. Collision checks apply to ordinary admin changes and hardening rotations on paired locks. Initial pairing retains its established command sequence, including locks without passcode-list support; it does not add a new listing prerequisite. Pairing likewise stages the candidate before sending it; a completed pairing with a lost admin acknowledgment retains an unconfirmed pending candidate rather than classifying it as applied.

## Offline evidence

- Host format tests cover full records, labels/seeds, maximum size, truncation, duplicate locks, invalid fields, unsupported headers and exact wire bytes.
- Crypto tests use known AES-256-GCM/PBKDF2 vectors and an independent reference, with wrong passwords and header/ciphertext/tag changes refused. Reuse existing test/vendor code without adding dependencies.
- Import tests exercise preflight, persisted-but-unreadable conflicts, capacity, failure at every write boundary, restart recovery and cleanup failure through a deterministic in-memory storage backend. Transport tests verify early authentication, bounded allocations and request ownership through a queued job.
- Hardening tests cover preview without catch-up writes, managed/admin preservation, provenance, partial failure, backup prerequisites and zero switch writes. Admin-code tests cover lost acknowledgements, reboot, pending candidates and failed reconciliation/persistence.
- Browser tests cover preview/confirmation, partial completion, export/import errors, longer job deadlines and honest state after failures.
- Both target builds, native tests, browser tests and source checks must pass. No HIL or device command runs in this pass.

The transport implementation accepts 16 KiB authenticated HTTP bodies and USB lines; unauthenticated HTTP remains limited to 8 KiB. Rendered replies have a separate 32 KiB limit, allowing existing lists above the request limit. Credential/passcode list preflight reserves 256 bytes for the response envelope and returns `too_large` before JSON construction if its content bound exceeds 32,512 bytes or the existing heap checks fail. This is a deliberate bounded-output policy; pagination is unchanged.

WebSocket admission allows at most 32 messages and 32,769 allocated payload bytes, including terminators and active batches. It counts buffer capacity, not just rendered length. A targeted result that cannot be rendered or admitted closes only that session's event sockets so pending browser jobs reject. Failure flags belong to admitted socket contexts, survive scheduling/closure failures, and are retried through service calls and the existing five-second sweep.

Native transport allocation tests bound owned JSON/text peaks, including the wiping cJSON allocator's aligned headers: 34 KiB for a 16 KiB request with one large parameter, 54 KiB for a maximum-size request near the 256-value limit, 34 KiB for a 16,000-byte request ID, and 28 KiB for an 11,000-byte result.

The backup handler fixture round-trips eight locks with exactly 8,192 plaintext bytes through the actual parser, dispatcher, manager, snapshot and restore code. Its 16 KiB export request uses a large request ID; its 16 KiB import request reaches the 256-value parser limit. Measured owned allocation peaks on the native host are 67,157 bytes for export and 49,679 bytes for import, within regression budgets of 80 KiB and 56 KiB. The export measurement includes 5,888 bytes for the eight existing manager lock objects. Both fixtures use inline USB dispatch; separate tests cover web authentication, confirmation, jobs and expiry.

These measurements count cJSON nodes and strings with aligned wiping headers, request IDs, request/response text capacity and terminators, snapshot records/metadata/views/arena, binary and base64 buffers, decoded views, existing/prepared manager lock objects and checked PBKDF2 scratch allocations. They exclude ordinary C++ string/container/function allocations, the NVS test backend, reference-HMAC vectors, fixture storage, allocator bookkeeping beyond cJSON headers, stacks, production PSA internals, TLS and other services. Native authenticated payloads use the independent crypto reference; target builds compile the PSA adapter but do not execute it. These fixture budgets do not establish total device heap availability or a hardware runtime peak.

Native builds fetch the exact cJSON component shared by both target lockfiles using the existing pinned `idf-component-manager==3.1.2` resolver. The build bootstrap verifies the locked content hash on download and cache reuse, needs no target build or full ESP-IDF installation, and performs no download from a running test binary. Run its tests with `uv run --no-project --with idf-component-manager==3.1.2 python -m unittest discover -s tools -p test_prepare_native.py`; `uvx platformio==6.2.0 test -e native` includes the production parser, dispatcher, HTTP, jobs and WebSocket host tests.

## Remaining acceptance

Runtime heap during derivation/import, physical-button behavior and a two-board restore remain unverified until separate hardware work is authorized. Full reset-button hardening additionally needs the switch-layout proof in issue #20. OTA and its hardware checks are deferred beyond v1.0.0.

The buffer-overlap contract follows the [PSA API conventions](https://arm-software.github.io/psa-api/crypto/1.2/overview/conventions.html#overlap-between-parameters).
